## 3. Tautological tests

Across the suite, **351 of 543 assertions (~65%)** are `assert.match`/`assert.doesNotMatch`
calls against the raw text of `app.js`, `author.js`, `cloudflare-worker.js`, `styles.css`,
`kaplan-brand-layer.css`, a migration file, or similar — i.e., the test reads the same file
the implementation lives in and asserts a substring the test author copied out of it. This
is the exact anti-pattern named in the task brief ("a test that greps SQL for a string it
copied from that same SQL proves nothing"), and it is not confined to SQL:

- **`scoring-contract.test.js`** — the clearest case. Both tests read a migration file and
  assert it contains strings taken verbatim from that same migration
  (`awarded_points := correct_pair_count *`, `pointsPerBlank`, etc.). No scoring math is ever
  executed. A scoring bug that changes *behavior* while leaving these substrings intact —
  or a refactor that changes wording while preserving behavior — is invisible either way.
- **`access-control.test.js`** — every one of its 11 tests regexes `cloudflare-worker.js` or
  a migration for evidence a check exists (`!hostSecret && !playerToken`,
  `can_access_live_media`, `roomState.phase !== "answer_reveal"`), but the Worker's
  `export default { fetch(request, env) {...} }` is never actually invoked. The Worker is
  the *only* place the service-role key is used and the sole enforcement point for private
  media — and it has zero executable test coverage. This is straightforwardly closable
  without live network calls: `fetch` is importable, and outbound Supabase calls can be
  stubbed via a mocked `fetch`/`env`, the same way `answer-submission-recovery.test.js`
  already injects a fake `client`.
- **`presentation-layout.test.js`** (22/22 tests), **`brand-layer.test.js`** (4/4),
  **`player-logo.test.js`** (6/8), **`late-join-bonus.test.js`** (2/3),
  **`door-bonus.test.js`** (5/8), **`reliability-contract.test.js`** (roughly 24/29),
  **`roster-identity-contract.test.js`** (3/3), **`video-clips.test.js`** (2/8) — same
  pattern to varying degrees: confirms code *exists*, not that it *works*.
- Two tests assert on **negative** presence (`assert.doesNotMatch`) as a stand-in for "the
  bug is fixed" — e.g. `"the old hardcoded door-background 50% gain override no longer
  exists"` and `"player and presenter branding uses plain BRAINSTORM text"` (no 🧠 emoji).
  These are real regression guards for a specific past incident, but they only catch
  *reintroduction of the exact old string*, not a different implementation of the same bug.

**Genuine counterexamples worth preserving as the model to extend:**
`quiz-core.test.js`, `quiz-validation.test.js`, `image-crop.test.js`, `subtitle-core.test.js`,
`video-clips.test.js`'s `video-utils.js` calls, `answer-submission-recovery.test.js`, and
`deploy-manifest.test.js` all import real functions and assert independently-derived
outputs. `deploy-manifest.test.js` is the standout — it's also the only test in the suite
that is currently, correctly, catching a real defect.

**One additional tautology risk inside a "good" test:** `quiz-core.js`'s
`tallyQuestionResults()` (host's "who got it right" summary) is a hand-written
reimplementation of `0030_multi_fill_in_the_blank_scoring.sql`'s comparison rules — the
file's own comment says so ("it intentionally mirrors ... if that migration's comparison
logic changes, this must change with it"). `quiz-core.test.js` tests `tallyQuestionResults`
thoroughly and well, but only against itself — nothing asserts the two implementations
still agree. A change to one without the other would make the host's live "got it right"
count *silently* diverge from the actual score, and no test would notice.

## 4. Failure paths (mistakes.md #10 ordering)

**Authorization boundaries.** Payload-shape allowlisting is well tested client-side
(`quiz-core.test.js`). The Worker itself — the only real enforcement point, and the only
holder of the service-role key — is untested as running code (see §3). No test proves a
request missing both `hostSecret` and `playerToken` is actually rejected, or that a
player's token from room A is rejected against room B.

**State transitions.** `submit_live_answer`'s revision/phase/question-id checks
(`0002_live_room_rpc.sql`) drive `answer-submission-recovery.test.js`'s excellent client-side
recovery logic, but the SQL transition rules themselves — phase must be `question_open`,
revision must match, question ID must match, `on conflict (session_id, question_id,
player_id) do update` making duplicate submissions idempotent — have no local executable
test at all. There is no Postgres/pglite harness in this repo; that's an infrastructure gap
worth a decision (build one, or explicitly accept SQL as review-only-verified).

**Reconnect/retry/duplicate/stale commands.** Player-side stale-revision retry is well
covered. Two things are not: (a) **host refresh recovery** — `PRODUCT_SPEC.md`'s "Sessions
recover after a host refresh using the stored room state and fixed quiz version" and
mistakes.md's release gate ("Host, player, and presentation can each refresh and recover in
every phase") have no test anywhere in the suite; grepping `test/*.test.js` for `refresh`
outside of the submission-recovery and title-caption tests returns nothing relevant. (b) the
duplicate-roster-entry bug fixed today (2026-08-17 changelog: "answers received count
sometimes showing roughly double") is regression-guarded only by regex
(`roster-identity-contract.test.js`), not by a behavioral test that actually calls
`acceptSubmission`/`acceptPlayerPresence` with two submissions from the same player and
asserts the roster doesn't grow.

**Schema compatibility with oldest fixtures.** This is the single most concrete, cheapest-to-fix
gap in the review: `quiz.sample.json` is loaded by **zero** tests, and
`music-trivia.question-bank.json` is loaded by **one** test for **one** field
(`betweenRoundBonus`). Neither fixture is ever run through `validateQuiz()`,
`toPlayerQuestion()` (every question, every type), or `tallyQuestionResults()`. `CLAUDE.md`
names both files as compatibility fixtures to validate "before shipping a schema change";
right now nothing would notice if a schema change broke either one.

**Layouts.** Extensive (22-test) coverage in `presentation-layout.test.js`, but 100%
textual — no visual/DOM assertion exists anywhere in the suite. mistakes.md #7 and the
release gate both explicitly call for visual snapshots per question type/scene; none exist.

## New additions to consider for `mistakes.md`

Not edited — for your decision.

- **A 15th lesson on the duplicate-roster bug (2026-08-17):** the root cause (broadcasting a
  locally generated auth token instead of the server-issued roster id as a cross-client
  `playerId`) is a distinct failure mode from lesson #3 (audio commands lacking identity) —
  it's the same *class* of bug (a distributed message missing/misusing a stable identifier)
  but on the presence/submission channel rather than audio. Worth its own numbered entry
  given the "What to do next time" for #3 doesn't mention presence/roster broadcasts at all,
  and this bug shipped after #3 was written.
- **A lesson on test-suite composition itself:** ~65% of this suite's assertions are
  source-text pattern matches against the file under test, including tests whose names
  promise behavioral guarantees ("late join boost ... caps at 2x", "resolved multiplier
  applies only to automatic scoring") that are actually satisfied by a regex on the SQL
  source. This is a variant of lesson #12 (changelog isn't engineering memory) applied to
  tests instead of commit messages: a green, fast, large-looking test suite can itself
  become a false signal if too much of it asserts "the code says X" rather than "the code
  does X." Given lesson #10 already prescribes a priority order for *writing* tests, a
  companion note on what makes a test *worth counting* toward that order would directly
  prevent this suite's current composition from recurring in the next project.
