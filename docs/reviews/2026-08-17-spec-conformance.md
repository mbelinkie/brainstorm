## 0. Headline: three findings that are more than documentation drift

These came out of the conformance pass but are code defects, ranked by CLAUDE.md's ordering.
Everything else in this report is drift.

### 0.1 Re-scoring a question inserts a second set of score events — priority 4/5

`questionJumpControls()` ([app.js:1014](app.js:1014)) renders a "Jump to any question" select in
the live host panel — not behind a debug flag; its only gate is `view === "host"` and a loaded
quiz. `jumpToQuestion()` ([app.js:400](app.js:400)) calls `setHostQuestion()`, which resets that
question to `phase: "lobby"`. The host can then press "Start question" (server phase
`question_open`) and reveal again. `lock_and_score_live_question`
([supabase/migrations/0030_multi_fill_in_the_blank_scoring.sql](supabase/migrations/0030_multi_fill_in_the_blank_scoring.sql))
re-reads the still-present `submissions` rows for that `question_id` and **inserts a fresh
`score_events` row per correct answer**. It never deletes prior events for the question, and
`score_events` has no uniqueness constraint — the only index is
`score_events_session_player_idx (session_id, player_id)`
([0001_initial.sql:91](supabase/migrations/0001_initial.sql:91)). Points double.

The back-navigation path is guarded — `showPreviousScreen()` ([app.js:436](app.js:436)) carries
an explicit comment, "Scoring is irreversible. Rewinding from a locked/revealed question to its
question card keeps submissions closed" — so the invariant was understood; the jump control simply
bypasses it. This is the same class as spec §7's "Duplicate submissions … do not create additional
score events" (line 302) and §3's "The host may reopen a question only through an explicit
override" (line 145). Recurrence of **lesson #11** (the score model was extended with modifiers but
replay/idempotency of the event log was never defined) and **lesson #1** (a control added for
testing convenience crossing into the live loop).

Cheapest durable fix is server-side, not in `app.js`: a partial unique index on
`(session_id, player_id, question_id)` where `created_by = 'system'`, or an explicit delete of
prior system events for that question inside the RPC before the scoring loop.

### 0.2 Two divergent copies of `validateQuiz`, and the tested one is not the one that runs — priority 3/6

`author.js:138` defines its own `validateQuiz`, and that is the function the editor actually uses
for import, download, and publish. `quiz-validation.js` exports a *different* `validateQuiz` that is
imported only by `test/quiz-validation.test.js`, `test/door-bonus.test.js`, and
`test/video-clips.test.js`, and shipped by `prepare-deploy.mjs`. Neither `app.js` nor `author.js`
imports it. They have drifted:

| Rule | `quiz-validation.js` (tested) | `author.js:138` (actually runs) |
|---|---|---|
| Unsupported question type rejected | no | yes (`supportedTypes`, [author.js:140](author.js:140)) |
| `fill_in_the_blank` accepted answers | **not checked** | checked ([author.js:211](author.js:211)) |
| `arrange_in_order` answer key | **not checked** | checked, incl. uniqueness + referential integrity |
| `categorize` answer key | **not checked** | checked, requires exactly 2 categories |
| `matching` key referential integrity | pair map presence only | clip→option IDs resolved |
| Per-question `audio.mediaAssetId` UUID | **not checked** | checked |
| Bonus audio asset IDs | `betweenRoundBonus.audio` | `finale.audio` — **a different field** |

The last row is the sharpest: the two validators check *different parts of the quiz document*.
Door/between-round audio asset IDs are validated only in the module nothing calls; finale audio
asset IDs are validated only in the module no test covers.

This directly contradicts CLAUDE.md's own claims — "`quiz-validation.js` … extracted logic that
tests import directly. **Prefer putting new logic here**; testability is the point"
([CLAUDE.md:84](CLAUDE.md:84)) and the invariant "validate against them via `quiz-validation.js`
before shipping a schema change" ([CLAUDE.md:151](CLAUDE.md:151)). Today, passing
`quiz-validation.js` proves nothing about what the editor will accept, and Phase 5's exit criterion
"Broken answer keys and missing assets are caught before a session starts"
([PRODUCT_SPEC.md:606](PRODUCT_SPEC.md:606)) is only met by the untested copy.

Recurrence of **lesson #8** (a compatibility/duplicate path left in place without regression
coverage) and **lesson #10** (checks added after the boundary was already complex).

### 0.3 `numeric_estimate` renders and submits but can never score — priority 5

`numeric_estimate` has player UI ([app.js:1244](app.js:1244), [1249](app.js:1249),
[1377](app.js:1377), [2043](app.js:2043)) and a contract test asserting that UI list
([test/reliability-contract.test.js:194](test/reliability-contract.test.js:194)). It has **no**
branch in any version of `lock_and_score_live_question`, is **not** in the author's
`supportedTypes`, and has **no** rule in either validator. A `numeric_estimate` question therefore
renders, accepts an answer, locks — and awards zero points to everyone, silently.

It is not hypothetical: the bundled compatibility fixture carries one.
`music-trivia.question-bank.json:226` holds `"optionalTieBreak": { "type":"numeric_estimate", …,
"answer":1982 }` — using an `answer` key that no code path reads (the shipped numeric type is
`closest_number`, keyed on `targetNumber`). It survives only because it sits outside `rounds`, so
neither validator walks it. The spec lists "Numeric estimation with tolerance" under **Later
formats** ([PRODUCT_SPEC.md:246](PRODUCT_SPEC.md:246)) — so this is a half-landed later format with
a live UI surface. Touches the CLAUDE.md invariant "Old quizzes still load."

## 9. Proposed additions to mistakes.md

Not written — `mistakes.md` was not modified, per the brief. These are candidates for your
decision, in that file's existing "What to do next time" format.

### Candidate #15 — I let a validation module fork, and tested the copy that does not run

`author.js` carries a private `validateQuiz` that gates every publish, while `quiz-validation.js`
carries a second, weaker one that only the tests import. They have drifted to the point of checking
different fields of the quiz document (`finale.audio` vs `betweenRoundBonus.audio`), and four
question types are unvalidated in the tested copy. A green `npm test` therefore proves nothing about
what the editor will accept. This is not a near-miss: the invariant "validate against the
compatibility fixtures via `quiz-validation.js`" is currently unprovable.

**What to do next time**
- One validator, one module, one import path. If a surface needs stricter rules, compose them —
  never fork the function.
- Add a test that asserts the shipped surfaces *import* the shared module, not merely that the
  module behaves.
- When a helper is extracted "for testability," delete the original in the same commit.
- Treat divergence between two copies of a rule as a release blocker, not a style issue.

### Candidate #16 — I made scoring irreversible in one navigation path and forgot the other

`showPreviousScreen()` carries an explicit comment that scoring is irreversible and refuses to
reopen a scored question. The "Jump to question" control, added as a testing convenience but
rendered in live host rooms, reopens any question with no such guard — and the scoring RPC has no
server-side defense, because `score_events` has no uniqueness constraint and the RPC never clears
prior system events. The invariant was known, written down in a code comment, and enforced in
exactly one of the two places that can violate it.

**What to do next time**
- Enforce idempotency at the boundary that owns the data. A client-side guard on one path is a
  reminder, not a constraint.
- For anything that appends immutable score-affecting events, define the replay rule *before* the
  first "jump", "undo", or "rewind" control ships: reject, supersede, or delete-and-rewrite.
- Any control labelled "testing" must be gated out of live rooms, or stop being labelled testing.
- Add a test that scores a question twice and asserts the leaderboard total is unchanged.

### Candidate #17 — I shipped a question type's UI without its scoring branch

`numeric_estimate` has player rendering, submit handling, and a contract test pinning it — but no
scoring branch in any migration, no entry in the author's supported types, and no validation rule.
It awards zero to everyone, silently, and an instance of it still sits in the bundled compatibility
fixture using a key (`answer`) that no code reads. The half-landed type survives because it lives
outside `rounds`, where no validator walks.

**What to do next time**
- A question type is one atomic unit across four surfaces: validation, scoring RPC, player render,
  presentation render. Land all four or none.
- Keep one canonical list of supported types and derive every surface from it, so a type cannot
  exist in three places and be missing from the fourth.
- Make the scoring RPC *fail loudly* on an unrecognized type rather than falling through to zero
  points — a silent zero is indistinguishable from everyone answering wrong.
- Validate every part of a quiz document, including sections outside `rounds`.

### Candidate #18 — the product spec stopped being the authoritative description and no one noticed

Two scoring modifiers, four question-type behaviors, an entire data model, and roughly a dozen
shipped features now live only in `CHANGELOG.md` and the code. `PRODUCT_SPEC.md` is named as
authoritative in CLAUDE.md and read first by every session, so its stale claims are actively
load-bearing — the `R = restart` line is the clearest example of a spec line that could damage a
live show.

**What to do next time**
- Any change that alters scoring, question formats, the data model, privacy boundaries, or host
  keyboard controls updates `PRODUCT_SPEC.md` in the same commit. Make that a release gate, not a
  courtesy.
- When a spec item is decided against, mark it *not built* in place rather than leaving prose that
  reads as a description of shipped behavior.
- Run a spec-conformance pass on a schedule, not only when someone notices drift.
